# 1. FR (기능 요구사항)

화면 설계·API 설계를 기준으로 역정리한 기능 요구사항입니다. 이후 범위 변경이나 재설계 시 이 문서를 기준으로 삼습니다.

- 표기: **FR-섹션.번호**, 우선순위는 **MoSCoW** (Must / Should / Could / Won't)
- 구현 여부는 문서 끝의 **구현 현황**에 정리했습니다 (2026-10 기준).
---

## 1. 온보딩 · 인증

| ID | 요구사항 | 우선순위 |
|---|---|---|
| FR-1.1 | 사용자는 이메일만으로 OTP(6자리 인증코드)를 받아 가입/로그인할 수 있어야 한다 (비밀번호 없음). 코드는 5분간 유효하고, 같은 이메일로는 60초에 한 번만 다시 받을 수 있다 | Must |
| FR-1.2 | 사용자는 가입 시 이용약관·개인정보처리방침에 동의해야 하며, 마케팅 수신 동의는 선택할 수 있어야 한다 | Must |
| FR-1.3 | 사용자는 가입 과정에서 카메라(모바일, 계약서 촬영용)·사진보관함·알림 권한을 요청받는다 | Must |
| FR-1.4 | 사용자는 언제든 로그아웃할 수 있어야 한다 | Must |

## 2. 계약서 분석

| ID | 요구사항 | 우선순위 |
|---|---|---|
| FR-2.1 | 사용자는 계약서 파일을 업로드(또는 촬영)하여 분석을 요청할 수 있어야 한다 | Must |
| FR-2.2 | 시스템은 업로드된 계약서에서 위험 조항을 식별하고, 조항별 예상 손실 금액을 산출해야 한다 | Must |
| FR-2.3 | 사용자는 분석 결과에서 위험 조항 각각의 원문·손실 사유·근거 법령·안전한 대체 문구를 확인할 수 있어야 한다 | Must |
| FR-2.4 | 사용자는 과거에 분석한 계약서 목록(히스토리)을 조회하고, 각 건의 결과를 다시 열람할 수 있어야 한다 | Should |
| FR-2.5 | 시스템은 분석 근거로 법령·판례 데이터를 참조해야 한다 | Must |

## 3. 소식 (콘텐츠)

| ID | 요구사항 | 우선순위 |
|---|---|---|
| FR-3.1 | 사용자는 소식(아티클) 목록과 상세 내용을 열람할 수 있어야 한다 | Could |
| FR-3.2 | 홈 화면은 최신 소식 일부를 노출해야 한다 | Could |

## 4. 전문가 상담 · 예약

| ID | 요구사항 | 우선순위 |
|---|---|---|
| FR-4.1 | 사용자는 상담 가능한 전문가(변호사/공인중개사) 목록을 조회할 수 있어야 한다 | Should |
| FR-4.2 | 사용자는 전문가별 예약 가능 일자/시간을 조회하고 예약을 신청할 수 있어야 한다 | Should |
| FR-4.3 | 사용자는 예약 신청 시 결제를 진행해야 하며, 결제 완료 시 예약이 확정돼야 한다 | Should |
| FR-4.4 | 예약은 신청 시점의 상담료를 기준으로 금액이 고정돼야 한다 (이후 상담료 변경과 무관) | Should |
| FR-4.5 | 사용자는 예약 상태(완료 여부, 요약)를 확인할 수 있어야 한다 | Should |

## 5. 구독 · 결제

| ID | 요구사항 | 우선순위 |
|---|---|---|
| FR-5.1 | 사용자는 구독 플랜 목록(가격, 혜택)을 조회할 수 있어야 한다 | Should |
| FR-5.2 | 사용자는 플랜을 선택하여 구독하거나 변경할 수 있어야 하며, 월간/연간 결제 주기를 선택할 수 있어야 한다 | Should |
| FR-5.3 | 사용자는 자신의 현재 구독 상태(플랜, 사용량)를 확인할 수 있어야 한다 | Should |

## 6. 계정 관리

| ID | 요구사항 | 우선순위 |
|---|---|---|
| FR-6.1 | 사용자는 자신의 프로필(이메일, 플랜)을 확인할 수 있어야 한다 | Must |
| FR-6.2 | 사용자는 알림 종류별(분석 완료, 예약, 마케팅, 공지)로 수신 여부를 개별 설정할 수 있어야 한다 | Could |
| FR-6.3 | 사용자는 개인정보처리방침을 열람할 수 있어야 한다 | Must |
| FR-6.4 | 사용자는 자주 묻는 질문(FAQ)을 확인할 수 있어야 한다 (정적 콘텐츠, 서버 저장 불필요) | Could |

## 구현 현황 (2026-10)

| ID | 상태 | 비고 |
|---|---|---|
| FR-1.1 | 구현 | 이메일 인증코드 + JWT. 처음 보는 이메일은 첫 로그인에서 자동 가입 |
| FR-1.2 | 구현 | 약관 동의는 화면에서 임시 보관했다가 로그인 직후 저장(`user_consent`, 이력으로 쌓임) |
| FR-1.3 | 일부 | 권한 안내 화면만 있다(web 정적 화면). 카메라·알림 권한 요청은 모바일 앱에서 구현 예정 |
| FR-1.4 | 구현 | 서버가 세션을 폐기한다 |
| FR-2.1 | 일부 | **PDF 업로드만**(web). 촬영은 모바일 앱에서 |
| FR-2.2 | 구현 | AI 서비스가 조항을 분류하고 정량화한다. **점수·등급 정의에 알려진 문제가 있어 화면에 노출하지 않는다**(06 참고) |
| FR-2.3 | 구현 | 조항 상세 화면(원문·사유·근거 법령·대체 문구). `precedents`는 RAG 전까지 빈 목록 |
| FR-2.4 | 구현 | 히스토리 목록, 다시 열기, 삭제. 실패한 분석도 목록에 포함 |
| FR-2.5 | **미구현** | 법령·판례 RAG(06 Phase 3). 지금은 유형별 고정 문구와 법령 이름만 쓴다 |
| FR-3.x | 미구현 | 홈의 소식 3건은 화면에 하드코딩 |
| FR-4.x | 미구현 | |
| FR-5.x | 미구현 | 프로필의 "이용권 관리"는 자리표시자 |
| FR-6.1 | 일부 | 이메일만 표시. 플랜은 "무료 플랜"으로 하드코딩 |
| FR-6.2 | 미구현 | 프로필의 "알림 설정"은 자리표시자 |
| FR-6.3 | 구현 | `/privacy` 정적 페이지 |
| FR-6.4 | 미구현 | 프로필의 "고객센터"는 자리표시자 |

## Won't (이번 릴리스 제외)

- FAQ의 서버 관리/검색 — 클라이언트 하드코딩으로 대체
- 전문가 상담사 본인의 자체 스케줄 관리 화면 — 상담사는 운영자가 직접 등록
